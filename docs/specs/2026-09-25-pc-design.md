# PCs in Galatea — design

Implemented by bridge 0.4, applier 0.10, steward 0.5 and brain 0.4, which carry this design as it
came out of their review (`docs/reviews/2026-09-25-pc-standards.md`, PASS 2026-09-27), and so
superseded by them. The standards' text wins where the two differ.

**Classification: architectural.** It adds a device class, sessions that belong to persons, a
device reached through a second path for waking, and a plugin model. These change interfaces that
three standards depend on, and none of their flows exists yet.

## What it is for

Home PCs and notebooks become governed devices in two ways:

- **The PC as a device.** Galatea wakes it, puts it to sleep, shuts it down, locks a person's
  session, and knows whether someone is using it.
- **Task plugins on the PC.** A plugin built for one task (a Kodi or mpv player, a game launcher)
  adds devices the house can control, such as "the player in the living room".

It is graded by HS19–HS25 (`docs/reference/2026-09-24-home-reference-scenarios.md`). General computer
use, an agent driving the screen, is out, by ruling (HS25). HS26, moving a person's films to a NAS,
came with ruling 7 and is not designed here yet (*Open*).

## Rulings it stands on

The maintainer, 2026-09-25:
1. General computer use is a separate problem; PCs are controlled through task plugins.
2. The capability model for plugins is "realistically very MCP shaped".
3. Plugins are hosted by the PC's bridge ("agreed for now"). The applier sees an ordinary bridge.
4. Order of work: scenarios, architecture, standard, reference implementation, for both parts.
5. **Confirmed by the maintainer, 2026-09-25:** an extension action from a plugin defaults to `confirm` until the owner lowers
   it. The maintainer answered "proceed" to this recommendation.
6. **A child's limit binds only while the PC is online.** A PC bridge enforces no standing limits of
   its own. A child who takes a laptop off the network is outside the house's reach, and the OS's own
   parental controls (Family Safety, Timekpr-nExT) are the answer for that.
7. **The brain is capable, but undisciplined and uninformed** (not designed here yet: *Open*). It can write scripts and use a
   console. Discipline, and most of the gates, are the brain's problem. Informing it is this
   project's: capabilities and provisioning for PCs, laptops and NASes, and perhaps routers (HS26).
8. **The brain acts through actions, for now.** The house does not hand a brain credentials or a
   console on its machines, even scoped to a job: "sandboxing stuff like this is a nightmare".
   What the brain can do on a PC or a NAS is what a device offers as an action, under the tiers
   (HS26).

Earlier rulings that bind it:
- **No premature policy.** Who may read or do what stays with implementations; only safety floors
  are MUSTs.
- **Prefer decisions a deployed fleet has tested.** A kiosk supervisor running on a fleet's
  computers, and a wake relay run as a separate component, are the precedent for the PC as a
  device.
- **Bridges bind to MQTT.** MCP stays inside the PC.

## Evidence

From research into LLM control of home PCs and into PC plugins:
- Every home platform integrates a PC through an agent on it that publishes status and takes named
  commands (HASS.Agent, LNXlink, System Bridge). That is a bridge's shape.
- Waking needs Wake-on-LAN, which comes from elsewhere and is unreliable on laptops and over Wi-Fi.
  Asleep and off look the same over the network.
- A system service cannot see user idleness or show anything on screen. Session state needs a
  process in the user's session. No OS can unlock a session remotely. A system service *can* lock
  or disconnect any session (`WTSDisconnectSession` on Windows; `loginctl lock-session` as root on
  Linux).
- The OS schedules a shutdown with a warning to the user: `shutdown /s /t 120 /c` on Windows,
  `shutdown +2` on Linux.
- MCP tool annotations are untrusted by the spec's own words. Tool lists may change at any time,
  and tools have no hash or version. The known incidents all attack the gap between approval and
  runtime; postmark-mcp changed code behind unchanged tools. The fix everywhere is pinning,
  signing and re-approval.
- Google fixes by platform rule which actions need confirmation, by trait, device type and
  direction. Alexa and Matter model "start a video" as a typed search, separate from transport.
- HASS.Agent runs any payload a custom command receives when its text is empty, a remote shell
  through MQTT. An OS "open this file or URL" handler runs executables and custom schemes.

## Rejected alternatives

- **Plugins add capabilities to the PC's own device.** Rejected: two plugins with `media` would
  collide, since a device has each capability once. A plugin's fault would also take the PC's
  power actions with it.
- **Each plugin is its own bridge on MQTT.** Rejected: every plugin author would implement bridge
  0.2 and hold broker credentials. Nothing would pin what a plugin does, and MCP servers could not
  be reused.
- **The applier as an MCP client of each plugin.** Rejected with ruling 3.
- **A separate "wake" device beside each PC, visible to people.** Rejected: the brain and the owner
  would have to know that a PC is two devices. A wake path on the PC's own device keeps one target.
- **Tiers that change with state** (sleep is `confirm` while someone is logged in). Rejected: tiers
  are static declarations (GA-DESC-3). A session in use is handled like an occupied room.
- **A lease from a person's use of the PC.** Rejected: a child unlocking once would lease the laptop
  against her own limit for two hours. Session keys change by themselves, as a thermostat's mode does.
- **A steward-side "delayed action with a warning".** Rejected for YAGNI: every OS already schedules
  a shutdown with a warning, so it is an argument of the action.
- **`ask(owner_approval)`,** a steward ask that only an owner answers (review, H6). Rejected for
  YAGNI: it collides with four confirmation rules. HS20 is served by a `notify` to the owner and the
  owner's own `define`.
- **`media.launch(uri)`, a `launcher` capability and `session.log_off`.** No scenario needs them.
  A URI opened through the OS shell is a remote shell.
- **A higher tier for `power.sleep` on a computer that cannot be woken remotely.** Rejected: a sleep
  keeps the session and anyone in the room undoes it with the power button. It is `reversible`.

## The model

### The computer class

A new class `computer`, added to the applier's closed list. A computer is one device, owned by the
PC's bridge (or by an adapter, *Computers behind an adapter*), and `feedback: closed`. Carrying its
own PC bridge, with the plugin devices that bridge hosts, does not make it `infrastructure`;
carrying the applier, the broker or another bridge does, as for any device (the box, if it runs a PC bridge). Its capabilities:

| Capability | Actions (arguments) | State keys | Idempotent | Stateless |
|---|---|---|---|---|
| `power` (new) | `wake`, `sleep`, `shutdown(delay_s?)`, `cancel` | none | yes, but `shutdown` no | **yes** |
| `session` (new) | `lock(account)` | `session.<account>` | yes | no |
| `notify` | `notify(text, urgency, from)` | none | no | yes |
| `sensor` | none | `battery`, `app`, `camera_in_use`, `microphone_in_use` | — | — |

**Power.**
- An asleep or off computer is `dead`: its bridge went offline gracefully. "On" is its liveness,
  so `power` has no state key.
- **The computer's own liveness.** The computer is the bridge's own host, so no protocol message
  checks it in. The bridge MUST observe its host at least every 10 s and count each observation as
  the computer's check-in (GA-BRIDGE-37). GA-BRIDGE-13's closed list of bound sources gains one:
  the bridge's own host, observed at least every 10 s, bound 30 s.
- `sleep`, `shutdown` and `cancel` end `delivered` on the bridge's `applied` ack (the OS
  accepted it), as any stateless action does (GA-APPLY-7). The device then goes `dead`, which is
  not a state change and so not `external`.
- `delay_s` schedules the action with the OS's own warning to every session. `shutdown` is
  `idempotent: false`, so an ack timeout never reissues it: a second scheduled shutdown errors on
  Windows and restarts the countdown on Linux. `cancel` withdraws a scheduled one; with nothing
  scheduled the OS has nothing to do, and the bridge acks `applied` all the same. Without `delay_s` the action is immediate. Whoever sits at the PC can also cancel
  a scheduled shutdown through the OS. That person is a local actor, like a hand on a wall switch,
  not an `ungoverned` path (which would cost the applier Safe, GA-DESC-6), and the house says so
  (HS23). So are the OS's own automations, a sleep when idle or a restart for updates: they are
  the device's own behaviour, seen as the computer going `dead`, as a thermostat's own schedule is
  seen in its state. Bridge 0.4 scopes GA-BRIDGE-32 to say so.
- `wake` is the exception (*Waking*).

**Going offline.** A bridge MUST publish the terminal ack of `sleep` or `shutdown` *before* its graceful `offline` (`graceful: true`) and before clearing its `lwt`, as GA-BRIDGE-22
orders a restart; otherwise the bridge is found dead while the step waits, and the step ends
`failed(no_ack)` (GA-APPLY-8). A bridge MUST also go offline gracefully on any suspend or shutdown the
OS announces to it (a closed lid). A will after an unannounced suspend is expected, and is not a
`bridge_fault`.

**Sessions.** One key per interactive OS account the bridge knows (not system or service
accounts): `session.<account>`, a scalar, one of
`active`, `idle`, `locked`, `disconnected`, `unknown` or `none` (not logged in). The bridge knows
accounts, not persons.
- `<account>` is a token the bridge derives, not the OS name: the account name when it already
  matches `[a-z0-9_-]{1,32}`, otherwise `u` and the OS's own account number (the Linux uid, the
  last part of a Windows SID). A name that itself matches `u[0-9]+`, or whose token another account
  already holds (a new `liza` after the old one was renamed), is never taken as it is: it gets the
  `u` form, so no two accounts share a token. The bridge fixes the token when it first sees the account, keyed by the
  OS's account number, and keeps it across its own restarts and the account's renames. It declares
  each token in `devices` with the OS name as its label, so «Ольга» or `john.doe` never becomes part
  of a key.
- **Every state key of a computer is `self_changing` by standard**: the session keys and the
  sensor keys (`battery`, `app`, `camera_in_use`, `microphone_in_use`). A person using the PC
  changes them with cause `device` (GA-EVT-6), so use takes no lease (GA-LEASE-2). Otherwise a
  draining battery or a switched window would lease the laptop for two hours. This departs on
  purpose from the applier's guidance to "declare only keys a person does not usually set": a
  person's use of a PC must never lease it against a rule (HS20). Applier 0.10 amends the guidance
  for keys the standard itself declares.
- **The key a lock sets is chosen by its argument.** For GA-EVT-1, GA-EVT-3, GA-BRIDGE-34's
  read-back and `already`, `session.lock { account }` sets `session.<account>` for that account.
- `session.lock(account)` is acked when `session.<account>` reads `locked` or `disconnected`
  (GA-EVT-3); it is `already` when it reads either, or `none`. If it ends `failed`, a
  level-triggered rule does not retry it until its condition becomes true again; the owner sees the
  failure as any rule's. The "moves towards" clause of
  GA-EVT-1 keeps its report caused by the apply.
- **`session.lock` takes no lease and is never refused by one**, named exceptions to the steward's
  GA-LEASE-1 and GA-LEASE-3. It only ever narrows use, and nothing should keep a rule from redoing
  it: otherwise a child who locks her own session at 20:55 holds the laptop against her limit for
  two hours, and a lease someone else took on the laptop stops her limit. GA-EVT-1 attributes the `locked` report to the
  apply by its correlation, which needs no lease.
- Who may lock whose session is the steward's policy. By the default tiers, anyone who may do a
  `reversible` action may lock any mapped session, which at worst makes its owner type a password.
- `idle` means no input for the bridge's idle threshold (default 300 s). There is no idle counter,
  so the key changes only when the state does.
- **Who sees what.** The system service sees `none`, `locked` and `disconnected` without any helper
  (on Windows through WTS session notifications and flags; on Linux through logind's `State`,
  `Remote` and `LockedHint`). Telling `active` from `idle` needs the session's helper. A logged-in
  session that is neither locked nor disconnected, with no helper running, reads `unknown`: a
  reading whose state cannot be derived, as the bridge standard already allows (GA-BRIDGE-1). It is
  not loss of contact, which stays `available: false`. Nothing reads `unknown` as free.

**Personal keys.** A state key may be declared `personal: true`. On a computer the standard declares
`app` (the foreground application of the active session), `camera_in_use`, `microphone_in_use` and
every `session.<account>` key personal. See *Personal readings*.

**Default tiers** gain rows:

| Class | Action | Default tier |
|---|---|---|
| `infrastructure: true` | `power.sleep`, `power.shutdown` | `no_voice` |
| `computer` | `power.shutdown` | `confirm` |
| any | an extension action from a plugin (*Plugins*) | `confirm` |

The `infrastructure` row sits with the existing one, before the class rows it must win over; the
extension row comes after all class, flag and load rows, and before the catch-all `any other`
row. Putting the box to sleep would take every
safety rule with it, which is why switching an `infrastructure` device off is already `no_voice`.

`power.wake`, `power.sleep`, `power.cancel` and `session.lock` stay `reversible`. A shutdown loses
unsaved work, which nothing undoes. The brain's reply about a shutdown with `delay_s` says that
whoever sits at the PC can cancel it, since `power` has no state to report the cancel (Brain 0.4).

The applier's closed list of sensor keys gains `app`, `camera_in_use` and `microphone_in_use`, and
its key rules gain the `session.<account>` family.

### Sessions belong to persons

The house model maps OS accounts to persons: a computer target gains `accounts: { <account>:
person id }`, keyed by the bridge's account tokens and set through `define`. The steward reads
session keys through it, and translates a
request about a person ("lock Лиза's session") into `session.lock { account }`. An account with no
mapping belongs to nobody the house knows, such as a kiosk account.

**A session in use is occupancy, for computers.** With `respect_occupancy`, a step that runs
`power.sleep` or `power.shutdown` on a computer:
- is `ask(in_use)` when any account **mapped to a person** reads `active` or `idle`;
- is `ask(in_use_unknown)` when none does, but a mapped account reads `unknown`, its key is absent
  or `stale`, or the computer has no `session` capability at all (fails closed, as GA-OCC-1 does);
- proceeds otherwise: every mapped account `locked`, `disconnected` or `none`. Unmapped accounts
  do not count, so the kiosk's session never holds up «Мы ушли» (HS21).

For a computer this check replaces the room check: a session says more about the PC than a motion
sensor in its room. (Amended by the standard review, round 2, W1: the session check comes first,
and when no mapped account says the PC is in use or unknown the room check still applies, so a
kiosk's film in an occupied room is not put to sleep; steward GA-OCC-3.) The two reasons mirror `occupied` and `occupancy_unknown`, and join
GA-STW-4's order beside them. A scheduled run turns either ask into a skip, as GA-SCN-4 does for
`occupancy_unknown`; GA-SCN-4 is amended to say so, and to say that a rule's run does the same.
`scenario_status` counts `skipped(in_use)` with `skipped(occupied)` as success, since a PC someone
is using is not a failure, and `skipped(in_use_unknown)` with the failed steps, as
`skipped(occupancy_unknown)` is: a run that knows nothing about a PC has not succeeded with it.
Without `respect_occupancy` (a direct request) the tier decides.

### Personal readings

A state key declared `personal: true` says what a person is doing. Personal keys need a principal
to check against, so:
- The steward's reads (`state`, `history`, `events`) gain an optional `endpoint` and, from a brain,
  a `speaker`, derived as GA-AUTH-1 and GA-AUTH-2 derive them for `plan`.
- **Floor:** the steward MUST NOT return a personal key's value for a read whose derived role is
  `guest`. An app or panel credential's endpoint comes from its binding. A read on a brain
  credential that names no endpoint has no role, and gets no personal values either. In `state`
  and `history` such a value is `withheld`, and in `events` it is replaced by `withheld`.
- A brain MUST name, in `state`, `history` and `events`, only an endpoint where the utterance it
  serves was heard: GA-BRAIN-4 extends to reads. Otherwise a brain serving a guest in the hall could
  name the owner's chat and read everything. A read that serves no utterance (the long `events`
  stream GA-BRAIN-15 needs) names no endpoint, and so carries no personal values.
- A brain MUST speak a personal value only in reply to the utterance whose read returned it
  (judged). Otherwise the owner's question at 20:00 answers a guest's at 23:40 from a cache.
- **The floor covers values, wherever they appear:** in `rule_fired`, and in `plan` and outcome
  payloads that carry state, as in `state`. It does not cover verdicts: `ask(in_use)`,
  `skip(already)` on a lock and the like tell whoever asked that a PC is in use. That is by design:
  HS21's panel has to say why it asks. A GA-BOX-1 grant on a device with personal keys is a grant
  to read them.
- The applier MUST mark personal keys in `describe`, and a bridge MUST declare them in `devices`.
  The owner may mark any other key personal through `configure` (raising only). Likewise the
  owner cannot remove a `self_changing` or `personal` declaration the standard makes.
- Who else may read them (the person themselves, a parent, the owner) is the steward's policy,
  left to implementations (HS23).
- **Said plainly:** personal keys are kept in the applier's and the steward's history like any
  other key, for the 7 days GA-STW-7 and GA-EVT-5 require. At Box, reading them needs the
  device's grant (GA-BOX-1). Below Box, any reader of the broker sees them.

Rules may read personal keys. A rule is the owner's, or one the owner's policy let a brain define
(GA-DEF-3, GA-DEF-6).

### Waking

A computer may have a **wake path**: a device field `wake_via`, naming another device that offers
`power.wake`. It is the owner's configuration: `configure` sets it on the applier, pairing the
computer with a wake relay's entry. The PC's bridge cannot know the relay. For a computer with no
`wake_via`, the applier removes `power.wake` from its declared actions.

- **The relay** is a bridge at level Serve, one per LAN segment, usually on the box. Its transport
  is the LAN interface, `up` while the interface has a link and the gateway answers ARP, which is
  an exchange the relay can make (GA-BRIDGE-23). Each entry holds a MAC in its bridge's
  configuration, has no class, is `feedback: open`, and is adopted by the owner like any device.
  Its `power.wake` declares `confirms: false`, so its `sent` ack is no fault (GA-APPLY-7). The
  relay bridge declares each entry `internal` in `devices`, and the owner may mark any other device
  `internal` through `configure`; an adapter's device named by a `wake_via` stays as its adapter
  declares it. An `internal` device is never shown to people, and never in rooms, groups or
  selectors, but `describe` lists it for the owner's app. (`internal` is a new flag, not
  `infrastructure`, which already means something else.) It is the
  steward's to enforce: selectors and groups leave `internal` devices out, as they leave out
  `infrastructure` and unadopted ones (GA-PLAN-6), and `define` refuses them in rooms and groups
  (beside GA-DEF-9). The applier still routes to the entry by id. `configure` refuses a `wake_via`
  naming an entry that is not adopted. A deployed fleet already runs a wake relay as a separate component.
- **Plan and apply.** `power.wake` on a `dead` computer with a `wake_via` is planned and dispatched
  to the relay's entry, not `skip(dead)` or `unreachable`. This is a named exception in GA-PLAN-4,
  GA-APPLY-9 and GA-APPLY-5, for this action only. For this step, "its bridge" in GA-APPLY-8
  means the owner of the `wake_via` device, not the computer's bridge, which is dead by
  definition. The steward only reports what the applier
  decides, so GA-STW-4 is unchanged. If the relay's entry is itself `dead`, the step is
  `unreachable`.
- **Outcome.** An ack from the `wake_via` device, final for that device but not for the wake (the
  relay's `sent`, or a Home Assistant switch's `delivered`), only moves the step along. A `failed(reason)` or
  `unsupported` from it ends the step as GA-APPLY-5 and GA-APPLY-7 would for that device:
  `failed(unreachable)` or `failed(expired)` is reported `unreachable`, any other reason as
  itself. The relay's entry is `feedback: open`, so on its own the wake would end `sent`
  (GA-STATE-4). The step is `acked` when the computer
  becomes `live` **and** each of its adopted hosted devices that was live when the computer died is
  live again or reported `available: false` (a definite answer, such as a plugin whose account has
  no session yet), within the action's `ack_within_s` (a new default row: `power.wake`, 90 s; 240 s after the standard review, round 5, OM3, to cover a cold boot and a plugin server's start); otherwise
  `failed(no_ack)`. The applier MUST keep which hosted devices were live at the computer's death
  across its own restart (GA-PERSIST-1). A computer's own status reappearing is the device's own
  report, so this is the one stateless action that ends `acked`, a named exception to GA-APPLY-7,
  GA-EVT-3 and GA-STATE-4.
- **The brain waits.** A wake can take longer than an utterance's 60 s lifetime. GA-BRAIN-17 is
  amended with one concrete exception: after the `acked` outcome of a `power.wake` made for an
  utterance, the brain may make **one** further write for that utterance, within the utterance
  lifetime of the outcome's time as the steward stamps it (not when the brain reads it), on the
  woken computer or a device it hosts. That write earns no further exception. GA-BRAIN-3's licence
  extends by the same rule. So in HS19 the brain can launch after a 70 s wake, once, and a brain
  back after an hour cannot.
- `power.wake` on a `live` computer is `already`: a named exception to the rule that stateless
  actions are never `already`.
- Any other action on a `dead` computer is `unreachable`, as today. The brain wakes first, waits for
  the outcome, then acts (HS19).

### Computers behind an adapter

A computer an engine exposes (HS24) fits the same model:
- An adapter's computer that its engine marks unavailable is `dead`, not `stale`: an exception to
  GA-STATE-3 for class `computer`, since an unavailable computer is asleep or off. Where the
  adapter can read the engine's availability, the computer is `live` while the engine marks it
  available, with no time bound: a named exception to GA-STATE-5, as a `feedback: open` device is
  live while its transport is up. Otherwise `configure` needs the owner's `fresh_s` before the
  computer is adopted.
- `wake_via` may name any device the applier can route to, a device of the same adapter included
  (Home Assistant's Wake-on-LAN switch). (Amended by the standard review, round 4, F4: GA-DESC-12
  maps an adapter's `power` only through an allowlist keyed by the agent's model, and the
  Wake-on-LAN switch belongs to another integration, so HS24's adapter offers no `power.wake`.)
- An adapter that cannot report sessions offers no `session` capability, and the computer then asks
  under `respect_occupancy` (above).
- An adapter maps to `power` and `session` only entities it knows: an allowlist keyed by the
  agent's model and its entities' `unique_id` pattern, never a generic button. Keying it per
  integration does not work, since an MQTT-discovery agent's entities belong to the engine's `mqtt`
  integration. Everything else on the computer is not offered, and is listed in the adapter's
  `ungoverned`. *Not checked by the harness:* the adapter cannot see what a button runs, and anyone
  on the engine's broker can announce an entity that matches the pattern.

### Plugins

A **plugin** is a package installed on a PC and hosted by its bridge. It holds:
- **a manifest**, in Galatea's terms, signed by its publisher;
- **an MCP server** that does the work, started only from the package's own files;
- optionally, **a skill** for brains. It is not standardised in this revision. Until it is, a skill
  never reaches a brain as instructions; it is third-party content, data under GA-BRAIN-3.

**The manifest** declares:
- `id`, reverse-DNS under the publisher's namespace (`org.example.kodi`), and `version`;
- its **devices**, each with a `key` stable across versions, a proposed class (or none), its
  capabilities, its state keys with `personal` and `self_changing` where they apply, a state
  cadence (for
  `basisMaxAgeMs`, GA-BRIDGE-13), and its **actions**. Each action has its arguments with
  constraints, `idempotent`, `stateless`, `confirms`, for a stateful action the state key and value
  that confirm it, a requested tier, and the MCP tool that implements it. The confirming value may
  name one of the action's arguments (`{ arg: "appid" }`), so `steam.running` confirms against the
  game asked for;
- **extension capabilities** under the publisher's namespace (`org.example.steam.launch`), with
  their schemas and descriptions, so that an LLM can read them at runtime;
- **tool hashes**: for each tool, a SHA-256 over the RFC 8785 canonical JSON of its `name`,
  `title`, `description`, `inputSchema`, `outputSchema` and `annotations`;
- the **command** that starts its server, naming only files inside the package, and the network
  hosts it may reach. A plugin MUST NOT fetch code at run time; that is the manifest's word, and it
  is not checked.

**Plugin devices** are separate devices hosted by the computer: a device field `host` names the
computer device. They share its bridge, so they go `dead` with it. A new class `player` covers media
players (HS19). A plugin device's class may be null. Its `stable_identifier` is `<plugin id>/<device
key>`. Changed by the standards review (round 7, RH1): the standards prefix it with the hosting
computer's own identifier, `<computer stable_identifier>/<plugin id>/<key>`, so that two PCs
hosting the same plugin do not collide.

**Install is provisioning, at a new bridge level, Host.**
- Host is independent of Provision: a PC bridge claims Host and not Provision, and a Zigbee bridge
  the reverse. GA-PROV-1 becomes per operation: `install` and `uninstall` need Host, and the other
  operations need Provision. Against a bridge that lacks the level an operation needs, it returns
  `not_claimed`.
- `provision { install: { host, package: { url, sha256 }, account } }` is owner-only (GA-PROV-1).
  The owner chooses the OS `account` (its token) the plugin runs as; a publisher cannot know it.
- The bridge answers `accepted` within its bound. It then fetches the package, checks its hash and
  signature, and keeps each installed file's SHA-256. Last, it sends an `installed` event carrying
  the manifest, or `install_failed` with a reason, as `commission` does. `uninstalled` follows an
  uninstall. The applier's `provision` event gains all three.
- The plugin's devices arrive unadopted (GA-ADOPT-1). **Adoption is the owner's approval:** the app
  shows each device's actions with the tiers they will have. **The server starts once any of its
  devices is adopted.** The bridge never calls a tool for a device that is not adopted.
- **A new version** is installed the same way, and is staged. Its devices carry the same stable
  identifiers (`<plugin id>/<key>`), and bridge device ids that include the version, so the two
  never collide. On the bridge's wire a device id is `<plugin id>:<version>:<key>`, since a device id
  in a topic cannot hold `/` (bridge GA-BRIDGE-18, GA-BRIDGE-69). A staged device's `devices` entry names the device it would replace
  (`staged_for`). The applier does not raise `route_conflict` for it; it issues a notice with cause
  `plugin_update` instead. Adopting it with `replaces` is hardware replaced by itself with the same
  identifier, so the identifier is not retired (GA-ADOPT-2), and the steward's names, rooms and
  rules are kept. GA-ADOPT-2 refuses a replacement that lacks an action the old declarations use;
  for a plugin device it is amended to allow dropping an action no safety rule uses, and the
  steward's steps on it become `unsupported_action`, as the replacement text already says. The bridge then stops the old server and drops its devices. What changed between
  the two manifests is for the owner's app to show. There are no automatic updates.
- **A changed action loses its lowered tier.** When a replacement changes an action's tool hash,
  schema or requested tier, the tier the owner set for it is not carried over: it falls back to the
  formula below until the owner sets it again.
- `provision { uninstall: { host, plugin } }` removes it. `install` and `uninstall` re-sent with
  the same `request_id` are answered as duplicates, as `remove` is.

**Tiers.** Let the floor of an extension action be the higher of its requested tier and whatever
the class, flag and load rows of *Default tiers* give its device. Its tier is the owner's
`configure` value if set, but never below that floor; otherwise the higher of `confirm` and the
floor. For a standard action on a plugin device: the higher of the standard's default and the
requested tier, raised by `configure`. GA-DESC-3 is amended: `configure` may lower an extension
action, down to its floor, and no other. Nothing lowers an extension action below its floor.
(Ruling 5, confirmed by the maintainer 2026-09-25.)

**Extensions reach clients.** The applier's rule "a client MUST NOT invoke an extension it does not
know" is amended: an extension described in `describe` with its schema counts as known. Its
description reaches a brain as third-party content, data under GA-BRAIN-3, as a skill would. The bridge's
`devices` document carries extension capabilities' schemas, descriptions and confirming keys to the
applier.

**Hosting floors**, on a bridge claiming Host:
- **Pinning.** The install directory MUST be writable only by the bridge's system service, and
  only the bridge verifies and starts a plugin's server, in the chosen account's session where it
  needs one; the session helper never does. At every start the bridge MUST verify the installed
  files against the per-file hashes it kept at install, and compare the live tools with the
  manifest's hashes. On
  every `tools/list` change it MUST compare again. A live tool absent from the manifest, a missing
  tool, a changed hash or changed files is a mismatch. On a mismatch it MUST stop the server, report
  every one of the plugin's devices `available: false`, and put a `faults` entry naming them, which
  reaches the owner as a notice (GA-BUS-12) (HS22). Only a reinstall of the adopted package, or of
  a new version, clears it.
- **No unapproved tools.** The bridge MUST NOT call a tool the manifest does not map to an action.
- **No authority to the plugin.** The bridge MUST NOT relay a plugin's elicitation or sampling. An
  action whose tool asks for input ends `failed(no_confirmation)`: the tool was already called and
  may have acted. No broker credential, confirmation token or user credential is passed to a
  plugin.
- **Least privilege.** A plugin's server MUST run as the account the owner chose, and never
  elevated: never SYSTEM or root; on Windows with the account's filtered token even when the
  account is an administrator; on Linux with `no_new_privs` set, so neither sudo nor a setuid
  program can raise it. An administrator's account is allowed, since a game launcher must run as
  its player (HS22). Said plainly, Windows' filtered token is not a security boundary: a plugin
  running as an administrator can raise itself. On Linux, `no_new_privs` does not stop what polkit
  or D-Bus grants the account. So least privilege is best effort on any PC, and
  the owner's app says at install that its administrators are other admins of it (below). The
  bridge SHOULD sandbox the server to its package files and declared hosts. If the server needs a
  session and the chosen account has none, its devices are `available: false` until one starts.
- **Commands.** A command's `value` becomes the tool's arguments. A tool result with `isError` is
  `failed` with a reason; a success is `applied` when the action `confirms`, and `sent` otherwise.
  An `applied` from a plugin is the plugin's word. The step is `acked` only when the confirming state
  key reports, as for any device.
- **State.** Each plugin device's state is a resource the plugin serves. The bridge reads it at the
  manifest's cadence, and also takes its change notifications where the server sends them. Each
  successful read or notification is the device's check-in (GA-BRIDGE-37), and its
  `basisMaxAgeMs` is 3 × the cadence, GA-BRIDGE-13's poll case. A quiet player is therefore still
  live, and a wake can ack.

**The PC's administrators are other admins of its devices.** Anyone with administrator rights on a
PC can stop its bridge, change its plugins, read its broker credential and publish as it. At Box
that reaches only the devices this bridge hosts (GA-BOX-1), so it is said per device, not in
`ungoverned`. Below Box a stolen credential reaches everything, but there Safe is not claimed over
bridges anyway (GA-DESC-6). A PC bridge MUST report `otherAdmins` on the computer and on each
plugin device: one `{ vendor: "os", label: <account token> }` per administrator account, re-read at
start and whenever the OS reports a change of the administrators group, a change being an event
(GA-BRIDGE-14). `ungoverned` would count against the whole applier's Safe claim
(GA-DESC-6), and one PC must not cost a home its leak valves. A safety rule on such a device then
needs `accepts_other_admins`, as GA-SAFE-6 already asks. The readings and plugin floors bind
everyone else (HS22, HS23).

A plugin's app may have its own network control: Kodi's JSON-RPC and web interface, a game
client's remote. The bridge reports it as `otherAdmins` on that plugin's devices (`{ vendor:
"kodi", label: "web interface" }`), unless the plugin disables it, never as `ungoverned`.

### No remote shell, anywhere

A floor for bridges and adapters alike: **no action executes its arguments as a command, script or
code, or hands them to an OS handler that may.** A bridge MUST NOT offer one among its own
actions. An adapter MUST NOT map
an engine entity that runs arbitrary commands (LNXlink's `bash`, a HASS.Agent custom command) to any
capability. For a plugin this is the manifest's word, checked by the owner at adoption; it is the
honest limit of the floor. An owner who adopts a plugin that drives a browser has chosen general
computer use for that device (HS25).

### Launching content

`media` gains an action and two keys:
- `launch(search)`: `search` is a typed object, following Matter's Content Launcher: `{ title?,
  series?, season?, episode?, kind?: movie · episode · music · channel }`. The device picks the
  item. `launch` is never `already` and `idempotent: false`: a reissue after an ack timeout would
  play another episode (GA-APPLY-6);
- state keys `title` (what is playing, or absent) and `started_at` (when the current item started),
  `self_changing` by standard on a `player`, with `playing`: an episode or a film ending is not a
  person taking the player, and takes no lease. On purpose, a person pausing with the remote takes
  no lease either: a lease on a player guards nothing worth two hours;
- `launch` is acked by a report received after dispatch in which `playing` is `true` and
  `started_at` differs from the value the applier held at dispatch. It compares values, never the
  PC's clock with the applier's, and is a named exception to GA-EVT-3's value match. Its default
  `ack_within_s` is 30 s, since a player may still be loading after a wake. The read-back
  (GA-BRIDGE-34) reports `playing`, `title` and `started_at`. The brain says the `title` the device
  reports (Brain 0.4). If the item ends and the next starts inside the ack window, the ack names
  the next one; the brain says the title it was given, which is then the one playing.

A device declares which search fields it supports through `args`, which gains a constraint form
for an object's fields (HS19).

### Rules: time windows and exceptions

For HS20:
- **A time-window condition.** A rule condition may be `between: { from, until, days }` in the
  home's timezone. Entering the window counts as the condition becoming true (GA-RULE-1). `days`
  names the day a window starts: 21:00–07:00 on Sunday to Thursday runs from Sunday evening to
  Friday morning. A `from` or `until` in a daylight-saving gap takes the first minute after, and one
  that occurs twice takes its first occurrence, as GA-SCHED-3 does for schedules.
- **A "not one of" condition.** A state condition may be `not_in: [values]`, true when the key
  reads none of them, `unknown` and an absent key included.
- **A rule of conditions only.** A rule whose trigger is only conditions (a time window, state
  conditions) has as its trigger those conditions held for 0 s, and is level-triggered: it fires
  when they become true together, and again each time they become true after being false.
- **Rule exceptions.** A rule gains `exceptions: [{ from, until }]`. A rule does not fire inside
  one. When an exception ends, a level-triggered rule whose condition holds fires, as when a lease
  ends (GA-LEASE-4).

HS20's limit is then a level-triggered rule: *between 21:00 and 07:00, Sunday to Thursday, when `session.liza` is
`not_in: [locked, disconnected, none]` → `session.lock { account: liza }`*. Killing the helper does
not escape it: the system service sees the lock without the helper, so the key reads `locked`, and
when Лиза unlocks it reads `unknown`, which makes the condition true again. The lock is done by the
system service, and takes no lease. The rule is false while the laptop is `dead` (GA-RULE-2), and
fires when it wakes. Лиза's «ещё полчасика» is a `notify` to Ольга's channel. Ольга grants it in her
app with a rule exception, as her own `define`.

A `notify` a guest asks for is free text from someone the house does not trust. `notify` gains an
argument `from`, in the applier and in the bridge's command value, which the steward sets on every
`notify` it dispatches and no caller may: `{ endpoint, role }` for a request, `{ rule }` for a
rule, `{ scenario }` for a scheduled run, and `{ notice }` for the house's own notices. The
applier refuses a `notify` without it. (Applier 0.10 accepts one for compatibility, and sends `from`
only to a device that declares it (GA-APPLY-14).) The owner's app and a computer's screen show it, so a
guest's text cannot pass for the house's own message. A `notify` on a computer is shown in every
logged-in session that is not locked.

**Offline.** A laptop taken off the network is `dead`, and a rule does not act on it, so the limit
binds only while the laptop is online (ruling 6).

## The reference PC bridge

Sentinel's shape on bridge 0.2, in two processes:
- **the bridge**, a system service. It holds the MQTT identity, status, will and roster, runs
  power actions and `session.lock`, hosts plugins, and supervises the helpers;
- **a session helper** in each user session. It reports whether its session is active or idle, and
  the personal keys, and shows notifications. It never starts plugin servers: the bridge starts
  them in the session itself. A logged-in session that is not locked or disconnected, and has no
  running helper, reads `unknown`.

A wake relay runs on the box. The first plugin is Kodi (HS19) or mpv, whichever the spike shows is
simpler. The reference bridge targets Linux and Windows. macOS has no supported way to read another
app's playback.

## Vocabulary

New terms for `CONTEXT.md`, written when the standards change:
- **Plugin:** a package on a PC with a manifest, an MCP server and an optional skill, hosted by the
  PC's bridge. *Avoid:* integration, extension (reserved for namespaced capabilities).
- **Session:** a logged-in OS account on a computer, mapped to a person by the steward.
- **Wake path:** the device, usually a wake relay's entry, that can wake a computer.
- **Personal reading:** a state key that says what a person is doing.

## Review

Round 1 (2026-09-25) had two readers: a spec reviewer, and a scenario walk of HS19–HS25 through
revision 1. The walk found five blockers:
- `sessions` was a list, but bridge readings are scalars;
- a person's use of the PC was `external`, so it took a lease;
- personal keys had no principal to check against;
- the wake could not be planned, and the relay was never live;
- HS20's rule could not be written.

It also found eight highs:
- the tier formula could not lower a tier;
- the pin missed a code-only change;
- `media.launch(uri)` was a shell, and its ack was undefined;
- a child could escape the limit;
- a PC's administrators were outside the gate;
- `ask(owner_approval)` collided with the confirmation rules;
- an adapter's PC did not fit;
- install could not answer in time.

The spec reviewer raised the same issues, plus four more:
- the kiosk session;
- the ack before the offline;
- known extensions;
- the time window.

Revision 2 answers each one. Keeping the limit offline was ruled out (ruling 6).

Round 2 (2026-09-25) read revision 2 the same way. The walk found two new blockers:
- a lock from any endpoint leased the laptop against the limit (now: `session.lock` takes no lease);
- listing a PC's administrators in `ungoverned` cost the whole applier Safe (now: `other_admins`
  per device).

It found four highs:
- the computer had no check-in or bound, so it read `stale` forever (now: the bridge observes its host);
- a wake over 60 s left the brain unable to launch (now: GA-BRAIN-17 amended);
- the least-privilege floor forbade Артём's own account (now: never elevated);
- a brain could read personal values through any endpoint it serves (now: GA-BRAIN-4 covers reads).

The spec reviewer found nine issues:
- `unknown` held only one way (now: what the service sees without a helper);
- account names were not ids (now: tokens);
- staged versions collided with the identity rules (now: versioned ids and `staged_for`);
- `internal` had no steward text;
- the personal floor used an applier term;
- Host's relation to Provision was unstated;
- `launch`'s ack compared two clocks;
- `days` was ambiguous across midnight;
- HS22 against the least-privilege floor (as the walk found).

Revision 3 answers these, and the mediums and lows of both reports: `launch` not idempotent; a
player's progress takes no lease; confirming values may name an argument; the install directory
writable only by the service, which alone starts servers; the allowlist by model and `unique_id`;
a changed action loses its lowered tier; `restart` dropped (YAGNI).

Round 3 (2026-09-25) read revision 3 the same way, and against the standards that had just passed
on `main`, merged into this branch. The walk found one new blocker: the computer's sensor keys were
`external`, so a draining battery leased the laptop and the limit was `refuse(leased)` (now: every
computer key is `self_changing`, and `session.lock` is never refused by a lease). Its high: a person
cancelling a shutdown was called an `ungoverned` path, which would cost Safe again (now: a local
actor). The spec reviewer found no blocker, and nineteen issues, among them:
- text written against the old standards (`unreachable` now `failed(no_ack)`; camelCase on the
  bridge's wire; the host as a bound source);
- "its bridge" for a wake step, and the relay's `confirms: false`;
- whether a computer is `infrastructure`, and the box's power tiers;
- the extension tier against the class rows;
- `in_use` merging "in use" and "unknown" (now two reasons);
- the lease exception filed under the wrong standard;
- brain reads serving no utterance, and cached personal values;
- the GA-BRAIN-17 exception made concrete and bounded;
- account tokens across a rename; the key a lock sets.

Revision 4 answers all of them, with the walk's mediums (the rule's trigger, a quiet player's
check-in, `no_new_privs`, the `notify`'s `from`) and most recommendations.

Round 4 (2026-09-25) found no blocker from either reader. The walk graded HS19 and HS22–HS25 as
designed, and HS20 and HS21 partly:
- `notify`'s `from` had no place in the applier's or the bridge's schema, so every notify would be
  refused (now: an argument in both, with forms for rules, runs and notices);
- plugin devices made their PC `infrastructure` when read literally (now: part of its own bridge).

The spec reviewer's mediums were the rule of conditions only (now: level-triggered, held for 0 s)
and what GA-BRIDGE-32 means on a PC (now: the OS's own automations are the device's behaviour, and

- `shutdown` not idempotent;
- `playing` `self_changing`, on purpose;
- standard declarations the owner cannot remove;
- GA-EVT-6 amended for an apply's own key;
- a token already taken falls back to the `u` form;
- the wake's outcome from any `wake_via` device;
- `launch`'s 30 s ack bound.

Round 5 (2026-09-25), a confirming pass over revision 5, **approved** it: no blocker or high, and

- **Mixed versions.** A 0.2 bridge refuses a `notify` carrying `from` (GA-BRIDGE-4), and GA-NOTE-1

- **A caller that sets `from`.** Say whether the steward refuses the request or overwrites it, and

- **HS21's `no`.** Ольга's `no` to `ask(in_use)` ends `skipped(not_confirmed)`, which

the session's scratchpad, and the dispositions will go into the standards' review record.

## Open

- **HS26 and ruling 7.** Informing a capable brain needs, at least:
  - a storage model: a NAS as a device, with its shares and free space;
  - reads that return documents (a file listing), not only scalar state, with personal results
    withheld as personal keys are;
  - file actions (copy, verify, move to the recycle bin) whose paths are held inside roots the owner
    declared, since a path argument is otherwise *No remote shell* by another road;
  - long jobs, and keeping a PC awake while one runs.

  Ruling 8 settles the access question: actions, not credentials, so *No remote shell* binds here
  as everywhere.
- **Ruling 5: settled.** The maintainer confirmed on 2026-09-25 that extension actions default to
  `confirm`, with lowering by the owner down to the floor.
- **Plugin state as an MCP resource.** It depends on MCP's `subscriptions/listen`, which the research
  did not test against a real server. The spike should.
- **Signing.** Whose keys, and what an owner sees when a package is unsigned. Candidates: MCPB's
  signing, or the git commit pin that Claude Code's community catalogue uses. For the reference
  implementation, a pinned `sha256` may be enough.
- **Skills.** How a plugin's skill reaches a brain, if at all.
- **macOS.** Only power and sessions, through the Companion app's sensors or a bridge. No player
  plugin on macOS for now.
