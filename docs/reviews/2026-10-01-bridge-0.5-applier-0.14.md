# Review — device extensions on any bridge

## Why

The first two devices on the Zigbee bridge's bench could not be described by the standards.

- **A vibration sensor** (Tuya TS0210) sends an alarm on every movement and never a clear. It also
  has a writable sensitivity setting. Neither fits the closed sensor keys (`temperature`,
  `humidity`, `motion`, `contact`, `leak`, `occupancy`, `battery`).
- **A button pusher** (Tuya Fingerbot Plus) has standard on/off plus seven settings: mode, limits,
  hold time, reverse and touch. Each setting is echoed by the device; a refused value is echoed as
  the old one. A mode change physically moved the arm, and it also changed what `on` does: in
  click mode it is a press every time, in switch mode a position. The device also sends about ten
  datapoints that no definition describes.

**Root cause** (the maintainer asked for it, 2026-10-01). A device can be described only by the
applier's closed vocabulary, so every device that does not fit needs a change to the standard.
The vocabulary is closed for a reason: it is what the gate and the default tiers understand.
The standards already have a self-describing path for everything else, extensions, but bridge 0.4
allows them on plugin devices only.

***What was checked first.** A deployed fleet's device model (a private research note).
- Its wire carries any scalar key. The meaning lives in rows an administrator enters.
- It has no events and no settings, and every workaround for a momentary signal left a recorded
  problem:
  - buttons re-armed by writing 0 back to the device;
  - a door sensor stuck "down";
  - an audio alarm reset to off on every reconnect.
- Its lessons are folded in below:
  - open keys live in their own namespace;
  - an event never feeds state, availability or freshness, and is never replayed;
  - a wrongly typed argument is refused.

**Rulings** (the maintainer, 2026-10-01):
- Fix the root cause: extensions on any bridge's device, a per-key `state` or `event` marker, the
  naming form settled, the closed core unchanged.
- Check the deployed fleet's experience first, then update the standard, then build the bridge.
- **The bridge re-describes.** A device's declarations hold for its current settings, and the
  bridge re-publishes `devices` when a setting changes them.
- **Undescribed keys are dropped and listed for the owner.**
- The PC build's extension-action schema widening, kept by the maintainer that morning, is folded
  in here, as its "next review".

## Round 1 change record

### Bridge 0.4 → 0.5

| Where | Rule | Direction | Why |
|---|---|---|---|
| *Devices*, `extensions` | Any device may carry `extensions`, not only a plugin device | **looser** | The root cause. Asked for by the TS0210 and Fingerbot benches |
| *Devices*, extension names | An extension capability's name is a namespace with at least one dot, under one its publisher controls: a plugin's `id` for a plugin, a reverse-DNS name of the bridge's maker for the bridge's own. Its actions and keys are the capability's name, a dot, and a name matching `^[a-z][a-z0-9_]*$`. A standard capability's name is never an extension's | **new** | The PC build's open item: the text gave the form by example only, and five schemas refused it |
| *Devices*, extension keys | Each extension key carries `kind`, `state` (the default) or `event` | **new** | The vibration alarm, a button press and a gesture are occurrences, not values held |
| *A device's status* | A device's status carries only the keys the device declares: its capabilities' state keys, its `sensorKeys` and its extensions' `state` keys. Anything else is left out (GA-BRIDGE-1, as it already said for plugin devices) | **stricter** for non-plugin bridges | In a deployed fleet, an undeclared `publishedAt` key would have shown every unknown device as on |
| *Devices*, `undescribedKeys` | A device entry lists the protocol's names for data the device sends that the bridge maps to nothing (`dp108`). This is for the owner only and is never a reading (GA-BRIDGE-76, new) | **new** | Ruling: drop, list for the owner. The Fingerbot sends about ten such datapoints |
| *Occurrences* (new) | An `event` key's value is published once, as an `occurrence` on the bridge's `event` topic `{ seq, instanceId, type: "occurrence", device, key, value, timestamp }`. It never appears in a device's retained status, never sets `available`, and is never re-sent after a restart or a snapshot. It is a check-in like any message from the device (GA-BRIDGE-75, new) | **new** | A deployed fleet's audio-alarm device was reset on every reconnect; a retained alarm replays. The event topic already has `seq`, de-duplication and gap detection |
| *Devices*, declarations | Every declaration on a device entry holds for the device's settings as last observed: `capabilities`, and each action's `idempotent`, `stateless`, `toggles`, `args`, `confirms` and `confirmedBy`. When an observed setting changes one, the bridge re-publishes `devices` within 1 s of observing it. A bridge that cannot observe a setting declares the worst case across its values (GA-BRIDGE-74, new) | **new**, stricter | Ruling: the bridge re-describes. Fingerbot `mode` turns `onoff.turn_on` from a set into a press |
| *Devices*, `confirmedBy` | Any stateful extension action carries `confirmedBy`, not only a plugin's | **looser** (wider) | A setting's echo is how a Tuya setting confirms: `mode` echoed as set, `delay = 20` echoed as the old 0. Its send has no protocol ack, so it is `confirms: false`, ack `sent`, and the applier's GA-EVT-3 match on `confirmedBy` acks or fails it |
| *Commands* | A command's `action` is a standard `capability.action` or an extension action by its full name | **looser** (wider) | Same as the naming row; `bridge/command.json` |
| Changelog, *Requirement index*, *Negative subjects* | Three new negatives: `publishes-an-undescribed-key` (GA-BRIDGE-1), `retains-an-occurrence` (GA-BRIDGE-75), `keeps-a-stale-description` (GA-BRIDGE-74) | **new** | Each new MUST needs a subject that breaks it alone |

### Applier 0.13 → 0.14

| Where | Rule | Direction | Why |
|---|---|---|---|
| *Devices*, `extensions` | Any device may carry them; each key has `kind` | **looser** | As the bridge |
| *Extensions* | Extensions reach the applier from any bridge's `devices`. Their descriptions are the bridge's or the publisher's words, third-party content for a brain | **looser** (wider) | As the bridge |
| *Action declarations*, `confirmed_by` | On any stateful extension action | **looser** (wider) | As the bridge |

### Steward 0.8 → 0.9

| Where | Rule | Direction | Why |
|---|---|---|---|
| *Tiers and confirmation* | "Except an extension action", not "an extension action from a plugin" | **looser** (wording follows the applier) | As the applier's extension row |

**Not changed, on purpose:**
- The closed core (classes, capabilities, sensor keys). A key moves into it only when a safety rule
  or a default tier needs it.
- Brain 0.6, voice 0.3. A brain sees extensions through `describe` already, as data.
- No `setting` marker beside `state` and `event`. A setting is an extension action with a
  `confirmedBy` key; the fleet's experience agrees a marker can wait.
- **The bridge's ack for a Tuya setting stays `sent`.** The echo is an observation, not a protocol
  confirmation (GA-BRIDGE-8), and it confirms through the applier's state match.

## Where to look hardest

- Whether "declarations hold for the settings as last observed" is testable, and what a bridge
  does before it has observed a setting (worst case?).
- An apply that both sets `mode` and then turns the device on, planned under one revision: the
  second step runs under the old declaration. Is "judged by the declarations it was dispatched
  with" enough?
- Whether occurrences need `history` at all, and whether a brain or the steward must see them
  (the steward's rules may want to trigger on one; that is steward work not in this round).
- Whether the extension tier floor is now too high for harmless extension keys such as a
  sensor's sensitivity, given that the owner may lower an extension action to its floor.
- Whether `undescribedKeys` leaks anything personal (raw data a device sends).
- Every place that still says "a plugin's extension" and means any extension.

### Reader B — Claude, no context

#### Round 1, no-context Claude reader: bridge 0.5, applier 0.14, steward 0.9

Readings: I = implementer, T = tester, A = attacker. No BLOCKER found.

#### HIGH

**H1 (I). The ack beats the re-description.** "every later step by the new ones" against "re-publish `devices` within 1 s". A `mode` step acks on its echo before `devices` arrives, so the next `onoff.turn_on` runs under the old declarations: `already` on a stale `on`, or sent as idempotent. GA-APPLY-2 checks the revision only at the start of an apply. Fix: publish `devices` before the status that carries the setting, and re-check the revision before each later step.

**H2 (I). `stateless` cannot be re-described.** GA-BRIDGE-74 lists "`stateless`", but *Devices* says "For `stateless` the applier's capability column wins". So click mode can never make `turn_on` stateless, and the motivating device stays undescribable. Fix: drop it from the list, or let a bridge declare a stateless pulse and say how it acks.

**H3 (I/T). An occurrence moves liveness after all.** GA-EVT-8 says "moves no liveness", yet the bridge says "Its report is a check-in like any message". The applier "judges liveness from the device's `last_check_in`". Fix: the roster's `lastCheckIn` moves as usual; only the `occurrence` event itself moves nothing.

**H4 (I/A). An owner's override survives a re-description.** GA-DESC-4 keeps the owner's `idempotent: true` "whatever its bridge or manifest says", and GA-DESC-15's fallback covers only "a plugin's extension action … tool hash". A re-declared press keeps `true`, and a reissue presses twice. An owner-lowered tier likewise survives a change of `args` (GA-DESC-11 covers only "a replacement"). Fix: GA-DESC-18 drops both overrides.

**H5 (I, cross-standard). The steward never relays occurrences.** GA-STW-7 and *Events and history* leave out `occurrence`, so brains never see a press or an alarm. If an implementer relays them anyway, GA-AUTH-7 covers only "that key's `state` events", so a personal occurrence leaks to a guest. Fix: relay `occurrence`, and extend GA-AUTH-7 to it.

**H6 (I/T). An unobserved setting is undefined.** "as the bridge last observed them" leaves three questions open:
- what a bridge declares after a restart, before a sleepy device re-reports;
- the worst case for `capabilities`, `args`, `toggles` and `confirmedBy`;
- whether the last observation persists.

"observing" is invisible on the wire unless the setting is a published key. Fix: such a setting MUST be a declared `state` key, with the worst case until it is observed, given per field.

#### MEDIUM

**M1 (T). The two field lists differ.** GA-BRIDGE-74 omits `extensions`, which GA-DESC-18 has. Neither has `wholeState`, `sensorKeys`, `feedback`, `personal`, `selfChanging` or `kind`. Fix: one shared list.

**M2 (T). `undescribed_keys` breaks GA-DESC-2.** It changes `describe` without moving `revision`, and nothing says when it is re-published. Fix: either call it a model change or exclude it from the model.

**M3 (A). Device-chosen strings reach the brain unmarked.** On IP protocols the device picks the names in `undescribedKeys`, unbounded. The steward passes "everything the applier describes" to a brain, with no third-party marking. Fix: a charset and a count bound, marked as data (GA-BRAIN-3).

**M4 (A). An outside party can starve every plan.** Each mode change from the device's app or button moves the house-wide `revision`, so every plan and every `configure` goes stale. Fix: scope staleness to the device, or rate-limit re-descriptions.

**M5 (T). De-duplication has an unmarked guess.** "within a few seconds" has no value and no ⚠️, and real repeated identical alarms merge. Fix: the transaction id plus a stated window.

**M6 (I). An event-only alarm on a closed key is stuck again.** A `leak` or smoke sensor that never clears must report under the closed key, so as a stuck state, the deployed fleet's failure. As an extension event instead, a safety rule cannot read it. Fix: rule for this case.

**M7 (I). Volume is unbounded.** The sensor alarms "on every movement", and `history` keeps every occurrence 7 days. Fix: allow coalescing.

#### LOW

- **L1 (T).** Negative subjects are missing for the personal-occurrence exception in GA-EVT-5, occurrence liveness, a safety rule reading an occurrence, and de-duplication. `plans-on-a-stale-declaration` also fails GA-DESC-2, which it does not list.
- **L2 (T).** The refusal of a safety rule that reads an event key has no error code.
- **L3 (T).** The schemas don't check *Extension names*: no prefix-equals-capability check, no key regex, and upper case and hyphens allowed in the namespace. Nested capabilities (`org.a`, `org.a.b`) are ambiguous under "everything before the last dot".
- **L4 (cross-standard).** The applier's own "`vendor.kiosk`" extensions escape the bridge's naming rule. Fix: one rule.
- **L5 (I).** `personal` is "state key[]" and bridge-declared only on computers and plugins, yet GA-EVT-5 excepts personal event keys. Fix: allow event keys, on any device.
- **L6 (A).** Box grants cover a device's `status` only, while occurrences ride the bridge-wide `event` topic. Fix: state the limit.
- **L7 (rules).** "A deployed fleet modelled an alarm as a state that never cleared" rests on a private note a stranger cannot check. Fix: drop it.
- **L8 (I).** The applier's `kind` is required, the bridge's `kind?` defaults to `state`. Fix: say the applier fills the default.

#### Looser moves

- **Extensions on any device.** Justified by the root cause, but its guard is the not-idempotent default, which H4 breaks.
- **`confirmedBy` widened.** Nothing forbids it naming an event key, so such an action can never ack. Fix: refuse at adoption.

No numbered sections and no `file:line` citations were found.

#### Findings

1. **HS3 and HS2: the motion hops (a PIR that never clears).**
   - **What breaks.** Many Zigbee PIRs send motion and never send a clear. The bridge cannot make up a clear: "A reading is only what the device reported: no optimistic state" (GA-BRIDGE-5). Bridge 0.5 also requires that "a key the applier's vocabulary already names … is reported under that name, never as an extension's" (*Extension names*). So `motion` stays `true` for good.
   - **HS3.** The rule "no motion for 180 s" never holds, so the hall light never goes off.
   - **HS2.** The room is `occupied` for good. This fails closed.
   - **Why the new marker does not help.** Declaring the key `event` instead would leave the edge rule with nothing to trigger on: steward 0.9 has no trigger on an occurrence. This is the very case 0.5 was written for, and it collides with the closed key.
   - **Fix:** let a closed sensor key be declared `kind: event`, and let a steward trigger and GA-OCC-1's "motion within the hold" read an occurrence's time.

2. **HS3 (the off rule on the dimmer), HS1 (the kettle step), HS18 (the lock's `battery`): self-changing keys take leases.**
   - **What breaks.** An extension state key that the device changes by itself (power, voltage, energy) has cause `external`. GA-EVT-1 says "Every state change the applier did not make, other than a `self_changing` key, appears with cause `external`". GA-LEASE-2 then gives each such change a `person` lease for 7200 s.
   - **Effect.** A metering dimmer or plug that reports every minute stays leased for good. The off rule is `refuse(leased)` for ever, since GA-LEASE-4 never runs.
   - **Why the bridge cannot prevent it.** The bridge's `selfChanging` row covers only computers, plugin devices and players. Before 0.5, a plugin's manifest could declare the key; now any bridge's own extension can produce one.
   - **Pre-existing too:** a lock's `battery` already does this.
   - **Fix:** an extension `state` key that no action's `confirmedBy` names is `selfChanging` by default. A bridge may also declare `selfChanging` on any device.

3. **HS4: the reopening hop, while the latch is held.**
   - **What breaks.** The latch refuses "every action that would change a state key the rule set" (*Latches*, GA-SAFE-7). The applier understands an extension "no further than its schema". A Tuya valve's countdown or a "power-on: open" extension action, whose `confirmedBy` is its own key, is therefore not latched. An app request with a person's token (`no_voice` floor) opens the riser while the floor is still wet.
   - **Fix:** while a latch is held, refuse every extension action on a device the rule actuated.

4. **HS11 and the house (a child applier holds the box's Zigbee): occurrences do not reach the steward.**
   - **Text.** GA-META-8's relay list and steward GA-STW-7's `history` list both omit `occurrence`.
   - **Effect.** An occurrence on a child applier never reaches the steward, and no steward's `history` returns one, so a brain explaining "what happened" (as in HS3) cannot cite one, though the applier keeps it for 7 days (GA-EVT-5).
   - **Fix:** add `occurrence` to GA-META-8 and GA-STW-7.

5. **HS18: the lock's events, and who opened the door.**
   - **What changes.** The Matter `LockOperation` events (source, user index) can now become occurrences.
   - **The gap.** GA-EVT-5 keeps them out of `history` only for "a key in the device's `personal`". The bridge's `personal` row gives no way for a non-plugin bridge to declare one, so "who unlocked" is kept for 7 days unless the owner adds the key.
   - **Fix:** let a bridge declare `personal` on any device's extension keys, and name operator identities as personal.

6. **HS13 and HS22: the scenario text.**
   - **Text.** "an owner may lower a plugin's extension action to `reversible` (GA-DESC-3, ruling 5)" is now narrower than GA-DESC-3: "an extension action, which it may lower to its floor".
   - **Fix:** say "an extension action, a plugin's or a bridge's own". Note that its floor is `reversible` only on a device that no class, flag or load row names.

7. **Not tied to a hop: GA-BRIDGE-74 after a bridge restart.**
   - **The gap.** The text gives no state for a setting that the bridge can observe but has not observed yet since its restart. A sleeping Tuya device answers no query.
   - **Effect.** Either the bridge publishes undefined declarations, or it publishes the worst case and then the observed value. The second gives a GA-DESC-18 model change for each such device on every restart, which refuses every plan in flight (GA-APPLY-2).
   - **Fix:** until it observes the setting, the bridge declares the setting's value from before the restart if it kept one, and the worst case if it did not. Say this explicitly.

8. **Not tied to a hop: a button pusher on a heating load.**
   - **The gap.** GA-BRIDGE-74 can turn a heating socket's `onoff.turn_off` into `toggles: true`. GA-SAFE-13 forbids `max_on_s` on such a socket, but `configure` enforces it and a bridge's re-description bypasses `configure`.
   - **Fix:** when a re-description makes a capped load's turn-off toggle, raise a notice and keep the cap as a `sent`-once notice path.
