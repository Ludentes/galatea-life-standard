# Review of the brain standard 0.1 and steward 0.2

The text under review is commit `4232718`. This record follows the `standard-review` procedure.

## Change record

Written and committed before any reader was dispatched. Directions: **stricter**, **looser**,
**moved**, **new**.

The brain standard is new. Its design (`docs/specs/2026-09-24-brain-standard-design.md`) went
through nine rounds of spec review before the maintainer approved it on 2026-09-24; those rounds are in the
design's git history, not here.

### The brain standard 0.1

| Rule | Direction | Why |
|---|---|---|
| GA-BRAIN-1: `answer` only for an utterance heard at the plan's endpoint after its `ask` event, with that utterance's record; never for an ask put on another endpoint | new | HS16. The steward trusts a brain's yes by ruling; this is the brain's side of that trust |
| GA-BRAIN-2: the answer's value is what was said (judged) | new | HS16: a relayed yes that no one said |
| GA-BRAIN-3: data never leads to a steward write unless an utterance asked to act on it | new | HS13: a calendar entry that gives orders |
| GA-BRAIN-4: a request names an endpoint where its utterance was heard | new | HS16 *Trust and guardrails*: the endpoint decides `via`, the role cap and the room, and the steward takes it on trust |
| GA-BRAIN-5: one utterance heard twice leads to one set of writes | new | HS1, HS5, HS6 |
| GA-BRAIN-6: no route around a refusal until a person asks again; two carve-outs (plan after an inline tier refusal; applying the plan that showed the refusal) | new | HS9, HS15 |
| GA-BRAIN-7: success spoken only for `acked`, `delivered`, `confirmed`, a `late_ack`, or a run `ended(done)` with no `failed_steps` (judged) | new | HS1, HS7, HS12, HS15 |
| GA-BRAIN-8: replies after an apply carry complete `reports` that match what the steward returned | new | Makes GA-BRAIN-7 gradable without reading prose as a decision |
| GA-BRAIN-9, GA-BRAIN-10: explanations cite `history` events that exist, and add nothing beyond them | new | HS3 |
| GA-BRAIN-11: a speaker named only from the endpoint's `speaker_hint`, never from the transcript | new | HS1, HS9: the steward trusts the named speaker by ruling |
| GA-BRAIN-12: a failure to serve an utterance is said within 10 s | new | HS11 |
| GA-BRAIN-13: unknown fields change nothing the brain writes | new | The steward's *Compatibility*, made testable |
| GA-BRAIN-14: the brain works through the front, steward and data servers it is given | new | So one harness can drive any brain |
| The front (`listen`, `say`), `speaker_hint`, `reports`, `cites` | new | The black-box ruling needs an observable front |
| Not required: architecture (resolver first, quarantined model, fallback), which models, what a cloud model is shown | **looser** than an architecture contract | The maintainer's ruling: black-box floors, no premature policy. Kept as SHOULDs |
| Not checked: an unknown verdict is `refuse`, an unknown extension is never invoked | **looser** than checking them | Client obligations in the steward's *Compatibility*; a black box shows them only through the steward's own refusal |

| Rule | Direction | Why |
|---|---|---|
| The `ask` event is `{ plan_id, step_ids, endpoint, time }`, its endpoint the plan's or its `confirm_on` (GA-CONF-5) | stricter | GA-BRAIN-1 needs to know where the question was put |

### The third-model reader

#### BLOCKER

**B1 — GA-HARN-2 has no mechanism [implementer, tester].** Steward: "The steward MUST take its clock from the harness (GA-HARN-2)" — but nothing delivers that clock. The applier solved this with `configure` accepting `time_source`, "an NTP server the harness runs" (GA-HARN-1); the steward's `define` change list (home settings, rooms, targets, groups, persons, endpoints, credentials, scenarios, rules, schedules) contains no time source, and no other operation carries one. Every lease, schedule, DST and expiry test depends on it. Two implementers will build two different clock hooks and both claim conformance.
Fix: give the steward the applier's `time_source` channel, harness-only, and name it in GA-HARN-2.

#### HIGH

**H1 — One utterance can answer several open asks [attacker].** GA-BRAIN-1: "`answer` is sent only for an utterance heard at the plan's endpoint after its `ask` event" — per plan, with no exclusivity. Two plans with asks open at once ("shut the water?" and "unlock the gate?"), one "yes" at the endpoint after both ask events satisfies the rule for both; `answers` is a per-step map with one optional `utterance` record, and GA-CONF-1/GA-CONF-2 check provenance and timing, never that the utterance already answered another plan. A fallible (not malicious) brain attributes the yes to the wrong question and a `no_voice`-adjacent `confirm` action runs on a question nobody heard. The record carries no binding the steward can verify.
Fix: an utterance record answers at most one plan; a second `answer` citing the same `{endpoint, time, transcript}` is `invalid_request`.

**H2 — The utterance-time check compares two unsynchronised clocks [implementer, tester].** GA-CONF-2: an answer "whose `time` is not after the `ask` event's, is `invalid_request`". The utterance's `time` is the endpoint's clock ("`time` when it was heard", brain.md *The front*); the ask event's is the steward's. Outside the harness ("the harness's one clock") nothing requires them to agree — skew rejects honest answers, and against a lying brain the check verifies nothing, since the brain asserts `time`. GA-BRAIN-1 inherits the same cross-clock comparison on the brain side.
Fix: either require endpoints and the steward to share a time source, or drop the comparison and say plainly the record is trusted whole.

#### MEDIUM

**M1 — The looser change widens speaker-hint blast radius [attacker].** Change record: `scenario_plan` takes `speaker?`, "looser — a named person, not a guest, may start a scenario at a shared satellite". A wrong or spoofed `speaker_hint` (whose provenance is explicitly undefined: "How an endpoint comes by it is not defined here") previously bought one request at that person's role; it now buys a whole run that "acts as that person, at `person` precedence" with per-step tokens (GA-SCN-3). Bounded by GA-BRAIN-11, but the amplification is real, and the symmetric tightening would not have shipped on the same evidence.
Fix: cap a speaker-named run at `member`, or require an endpoint with a `person` for owner-role runs.

**M2 — GA-BRAIN-6 "same action on the same device" is undefined [implementer].** "After one, a brain MUST NOT seek the same action on the same device again … until an utterance asks for that action again." Are args part of "the action"? If a person asks for scenario "movie night" by name and one step was earlier refused, is that "an utterance asks for that action"? The text lists "running any scenario with a step for that action on that device" as a route around, so the literal reading blocks the scenario the person just requested.
Fix: define sameness as `(action, args)` and state that naming a scenario asks for its steps.

**M3 — GA-BRAIN-12: failure undefined, data servers missing, clock starts too early [implementer, tester].** "because its model, its uplink or the steward failed" — a dead data server ("what's on my calendar?") is none of the three; "failed" versus merely slow is nowhere bounded, so a brain that waits 12 s and answers correctly both complies and doesn't; and the 10 s run from the utterance's `time` (when heard), not from delivery to the brain, so a brain that polls `listen` late inherits a spent budget.
Fix: measure from `listen` delivery or grant a minimum grace; add data-server failure.

**M4 — Wire requirements with no negative subject [tester].** GA-BRAIN-13 and GA-BRAIN-14, and the steward's new GA-CONF-5, are `verify: wire` but appear in no negative-subject row. By the applier's own rule ("a requirement whose negative subject passes is disarmed"), checks that silently always-pass are only caught by subjects; these three have none.
Fix: add subjects (`reacts-to-unknown-fields`, `skips-the-ask-event`, `calls-around-the-front`).

**M5 — Arbitration window: chaining and "identical" [implementer, tester].** "times within the arbitration window" — pairwise, or from the cluster's first? Utterances at t=0, 1.9, 3.8 s pair within 2 s but span 3.8. And GA-BRAIN-5's MUST covers "identical transcripts" while "how near-identical transcripts are matched is the brain's choice" — so `double-fires` can only ever test byte-identical duplicates.
Fix: the window opens at the first utterance of the cluster; say so.

#### LOW

**L1 — Constants gating MUSTs are self-declared guesses [tester].** "Both are guesses until measured": arbitration window 2 s gates GA-BRAIN-5, failure bound 10 s gates GA-BRAIN-12.

**L2 — `listen`'s `wait_s` has no range [implementer].** The applier bounds `events` `wait_s` at 0–30; the front's twin operation says nothing. Also, utterance `time` is nowhere said to be RFC 3339, which the applier mandates for its times.

**L3 — Scope statements with no id and no disclaimer [tester].** "A brain is a client of exactly one steward… It is never an applier's client" — normative, unverifiable by a harness that plays only front/steward/data, and brain.md omits the applier's cover sentence "A MUST with no id binds a party the harness cannot test and says so."

**Process note:** steward frontmatter still reads `version: 0.1` with no 0.2 changelog row — correct before the bump, but the row must land with it.

### The third-model reader

The sandbox declined `python3 conformance/check_manifest.py` (command not approved), so I could not re-run the mechanical floor myself; the change record reports it green at `1acb760`, and I reviewed the text at HEAD (`4ed3f6c`) directly. Findings from the three readings:

### Independent review — brain 0.1, steward 0.2 (text at `4ed3f6c`)

#### BLOCKER

**B1 — The front has no security floor, and every trust ruling stands on it** [attacker]. The applier has GA-SEC-1, the steward GA-SEC-2 ("Every connection MUST use TLS unless both ends are on one host's loopback"); brain.md's *The binding* ("MCP over Streamable HTTP, one tool per operation… The endpoint side runs the MCP server; the brain is its client") requires neither TLS nor authentication on the brain↔endpoint link, and no GA-SEC id exists in the brain index. That link carries `transcript` and `speaker_hint` — the exact values GA-BRAIN-1/GA-BRAIN-11 relay and the steward "takes… on trust". A network attacker injects `{ transcript: "да", speaker_hint: "owner" }` and every gate above passes. The ruling makes the trust "not unforgeable"; it does not excuse the only standard without a transport floor. Fix: add GA-BRAIN-16 mirroring GA-SEC-1 for the front and data-server connections.

#### HIGH

**H1 — `failed_steps` contradicts step-level success** [tester/implementer]. `scenario_status` returns "`failed_steps`… for every step that did not end `acked`, `delivered`, `sent` or `skipped(already)`". A step whose final outcome is `confirmed` (GA-WIT-1) — which GA-BRAIN-7 names a success ("speak of success only for `acked`, `delivered`, `confirmed`…") — lands in `failed_steps`, and GA-BRAIN-7 then defines the run as not a success ("`ended(done)` with no `failed_steps`"). Same for a by-design `skipped(occupied)`. Two implementers resolve this differently; nothing says whether a run waits for witness verdicts. Fix: whitelist `confirmed` (and decide `skipped(occupied)`), or say a step ends only when its witness verdict is in.

**H2 — GA-BRAIN-15 omits the success→failure transition** [implementer/tester]. The follow-up duty triggers only for "a step or run the brain spoke of as under way (`applied`, `running`), or as failed". A step spoken of as `acked` whose witness then reports `unconfirmed` — the very transition GA-BRAIN-7 recognises ("a witness verdict, once present, governs over `acked`") — has no MUST to be said unprompted. The brain that announced success stays silent when the witness disagrees. Fix: extend the trigger to any final outcome differing from what was said, success included.

**H3 — Rule-firing idempotency key collides within the clock's resolution** [implementer]. GA-STW-10: "a rule's firing uses the rule id and the firing's time". Nothing specifies sub-second precision. Two edge-triggered firings of one rule in the same tick produce one key: same body → the applier returns the first apply and dispatches nothing (a real firing silently swallowed); different body → `idempotency_conflict`. Fix: add a per-rule sequence number to the key.

#### MEDIUM

**M1 — GA-HARN-2 is thinner than GA-HARN-1 where it matters** [implementer/tester]. The applier's text says the subject takes time "elapsed time included: the harness moves time forward by stepping that clock, and the subject honours the step"; the steward's says only "takes all time from the `time_source` set by `define`". Every lease, schedule and DST case needs stepped time, and `time_source` appears nowhere in the Home settings the house model lists. Fix: copy GA-HARN-1's stepping sentence and list `time_source` among the home's settings, harness-only.

**M2 — "An `app` endpoint always has a `person`" has no enforcement** [implementer]. No `define` refusal and no id backs the invariant (GA-DEF-8 covers only voice-without-`served_by`); an app endpoint with `person: null` falls under "No person means a guest", contradicting the sentence, and the `max_role` defaults don't cover the case. Fix: `define` refuses an app endpoint without a person, with an id.

**M3 — Unregistered `speaker` is undefined** [implementer]. The steward says the brain "MAY name a registered person as the speaker" but never says what a request naming an unregistered person id gets — error, guest, or trust. GA-BRAIN-11 tells the brain to relay the hint without checking registration. Fix: name the error (`invalid_request` or `not_permitted`).

**M4 — GA-BRAIN-6's "same action" misses equivalent actions** [attacker]. "MUST NOT seek the same action on the same device again, with any arguments" — after `refuse(leased)` on `onoff.turn_off`, `level.set_level(0)` on the same device is a different action by the letter and defeats the rule's purpose; the harness grades the letter. Fix: "the same action, or another action setting the same state key".

**M5 — The `scenario_stop` `speaker?` loosening amplifies spoofed hints, unexamined** [attacker]. The change record marks `define`/`scenario_stop` taking `speaker?` as **looser** and argues only `define` ("otherwise HS1, HS6, HS10 cannot happen"). For `scenario_stop` a spoofed `speaker_hint` of the owner at a shared satellite now stops any person's run (GA-SCN-9 compares the *named* person's role) — the third-model reader's M1 deferral covered `scenario_plan`, not this. The symmetric tightening would not have shipped on that justification. Fix: cap a speaker-named stop, or record the maintainer's ruling as for M1. (Likewise note GA-CONF-2's looser 1 s pre-ask tolerance now lets an answer cite an utterance that predates the question; bounded, but looser under clock uncertainty.)

#### LOW

**L1 — Constants row hardcodes a configurable default** [tester]. "Plan expiry | 60 s; 300 s with an `ask` step" contradicts `ask_expiry_s` being owner-settable; the row should read "`ask_expiry_s` with an ask step".

**L2 — GA-CONF-1 leaves the answering credential unstated for `confirm_on`** [implementer]. "only from that one" names the endpoint; whether any credential bound to it may answer is unsaid.

**L3 — Occupancy: "all its sensors have been `live`"** [implementer]. Reads as every sensor in the room — a dead temperature sensor then blocks `vacant` forever; presumably only occupancy/motion sensors are meant.

For a brain-served answer the yes is an utterance with `available_at`; for an app answer there is no utterance record, and the brain learns of it from an `answer` event or the plan's state. Which timestamp starts the 60 s — the event's steward time, the brain's receipt — is unsaid. This is exactly the path round 4's R H1 fix was made for; two implementers read it two ways, and one reading (receipt time) makes GA-BRAIN-17 toothless for `confirm_on` plans.
Fix: "counting from the `answer` event's time" (or the utterance's `available_at` when there is one).

**N4 — GA-BRAIN-1's index row drops "whom the `answer` names too"** [tester]. Body: "only for an utterance whose `speaker_hint` names that speaker, whom the `answer` names too (GA-BRAIN-1)". Row: "only for an utterance whose `speaker_hint` names that speaker". The manifest is generated from the row, so the graded requirement never tests that the answer names the speaker; the steward-side check (GA-CONF-1) is the steward harness's, not the brain's. Same row/body drift class as round 5's F1, F4, F7.
Fix: add "the answer naming that speaker" to the row and regenerate the manifest.

**N5 — Round-5 tightenings landed with no negative subjects** [tester]. GA-CONF-4's new clause ("a later change to what a brain serves included"), GA-SEC-2's new certificate validation (the steward has no TLS subject at all, and this revision made the row stricter), and GA-CONF-2's new step-not-in-`step_ids` refusal are all `wire` MUSTs appearing in no negative-subject row — the class the record itself fixed twice (round 1 M4, round 3 K M4). A harness that never flips `served_by` onto a `confirm_on` endpoint reports `pass` forever.
Fix: extend an existing subject or add one exercising a `define` that brain-serves a `confirm_on` endpoint.

**N7 — The resume after `listen`'s `cursor_expired` is shaped nowhere** [implementer]. "A `cursor` older than the front keeps is `cursor_expired`, and the brain resumes from the oldest it keeps."
