# Review of the bridge standard 0.3 and applier 0.9, discovery

This record follows the `standard-review` procedure. The commit reviewed is named with pass 1.

## Change record

Written and committed before any reader was dispatched, and before the text itself. Directions:
**stricter**, **looser**, **moved**, **new**, **renamed**.

This revision adds discovery, and nothing else. The maintainer ruled on 2026-09-25 that a finder on the
box owns the discovery listeners, that bridges declare what they can take as data in a manifest,
and that candidates reach the owner through the applier. The design is
`docs/specs/2026-09-25-discovery-design.md`, which passed three rounds of spec review; its
evidence is research into network discovery. The items already carried to
applier 0.9 by the last review (an idempotency key for `provision`, a transmitter that answers
nothing, GA-META-10 under parallel applies, an open-loop device's state) are not in this revision.

### The bridge standard 0.3

| Rule | Direction | Why |
|---|---|---|
| A new level, **Find**, claimed only by a finder, in its own `status` | new | The finder is not a bridge: it holds no device and takes no command |
| *The finder*: one process per box; mDNS, SSDP, DHCP, Bluetooth, USB; the only holder of `CAP_NET_RAW`, the host network and the Bluetooth adapter for discovery | new | The ruling. Home Assistant, openHAB and Homey have this shape (research) |
| GA-FIND-1: the finder connects, publishes `status` and dies as a bridge does | new | The applier judges its liveness as it judges a bridge's (ruling 14) |
| GA-FIND-2: the finder sends only mDNS queries and SSDP M-SEARCH, connects to no device, holds no credential, publishes only under `{root}/finder/` | new | It holds the most network privilege of any component, so it does the least with it |
| GA-FIND-3: a candidate only for a match of an installed manifest; hearings that share a key merge; `id` never changes while the finder runs | new | An ignore and a `connect` must name a stable thing |
| GA-FIND-4: `candidates` re-published within 1 s of a change; dropped after 24 h unheard (⚠️ a guess), or at once on an mDNS goodbye or a USB unplug | new | The 24 h is a guess; it gates only how long a gone device stays listed |
| GA-FIND-5: `status` lists every source, `off` for one the finder cannot use | new | The owner must see that DHCP is not heard, rather than conclude nothing is there |
| *The manifest* (`galatea-bridge.json`): `bridgeType`, `name`, `version`, `connect`, `matchers`; matcher fields are Home Assistant's, in camelCase; the schema is `conformance/galatea-bridge.schema.json` | new | Home Assistant's matcher vocabulary covers its whole catalogue (research) |
| GA-BRIDGE-39: a bridge type that ships a manifest ships a valid one, and its bridges give its `bridgeType` in `status` | new | The applier matches candidates to running bridges by it |
| `bridgeType` in `status` and `connections` on a device and a transport are **optional** | **looser** than a required field | Compatibility: a 0.2 bridge still conforms. A bridge without `bridgeType` takes no candidate; one without `connections` leaves its candidate listed |
| GA-BRIDGE-40: `connect { requestId, issuedAt, address, keys, credential? }` ends in `connected` or `connect_failed`; `invalid_request` from a bridge whose manifest does not say `connect` | new | The ESPHome case (HS27) |
| GA-BRIDGE-41: a device's or transport's `connections` carries every identity key the bridge knows for it | new | Without it a held device stays a candidate |
| GA-BOX-1: only the finder writes `{root}/finder/#`; only the box's bridges and applier read it | stricter | A candidate list is a map of the home's network |
| A `credential` in `connect` rides the binding, readable by a wildcard reader below Box | new, stated | As the Matter setup code already does. Below Box, everything on the broker is readable |
| A restarted finder may give new candidate ids | **looser** than ids that survive a restart | Ignores are kept by key, so nothing depends on an id surviving |

### Applier 0.9

| Rule | Direction | Why |
|---|---|---|
| `candidates`, a new operation at Act: `{ finder, candidates }`, each with `offers` naming the live bridges that can take it; the configuration credential's only | new | The owner has one place to look (the ruling) |
| The configuration credential's list gains `candidates` | **looser** for that credential | It already holds `provision`, which is stronger |
| No `candidate` event | new, stated | `events` is one stream every client reads; a candidate is not a brain's business |
| `configure.ignore_candidate` and `unignore_candidate`, stored by key, persisted | new | GA-DISC-3 |
| `provision.connect { candidate, bridge, credential? }`: `not_claimed` unless the bridge is this applier's, claims Provision and gives a matching `bridgeType` with `connect: true`; `unreachable` for a dead one; `invalid_request` for an unlisted id | new | GA-PROV-1's pattern |
| GA-PROV-1 names `connect` beside `commission` | wider | The same credential, the same routing |
| The `provision` event gains `connected { bridge, device or transport }` and `connect_failed { bridge, reason }`; GA-EVT-5 and GA-META-8 carry them | wider | GA-EVT-5 and GA-META-8 already carry `provision` |
| The finder read like a bridge; a `status` without a known `v` makes it `dead`, with no `bridge_fault` | new | GA-BUS-14's rule, without the devices it protects |
| The meta-applier: candidates and ignores belong to the applier that owns a box's bridges; the meta-applier offers only its own; `connect` for a child's bridge is `not_claimed` | new | As for `provision` today |
| Two boxes on one LAN may each list a device the other's bridge holds | **looser**, a stated limit | A meta-applier cannot see its children's `connections`. Taking it twice is the owner's choice, as configuring two engines for one device is today |
| GA-DISC-1: a candidate is never a device | new | Found is not adopted |
| GA-DISC-2: `candidates` lists only candidates neither ignored nor held, only to the configuration credential | new | |
| GA-DISC-3: an ignore hides every candidate that shares a key with it, across restarts and addresses | new | |
| GA-DISC-4: `provision.connect` goes only to a bridge that can take it | new | |

### The steward and the brain

No change. GA-STW-7 already relays the applier's `provision` events, so `connected` and
`connect_failed` pass through. No candidate reaches a steward or a brain.

### The threat reading readers should test

Discovery is unauthenticated. Anyone on the LAN can announce any service, and can announce a key
already known, which moves that candidate's `address`. The standards never trust a candidate:
- it is never a device (GA-DISC-1);
- a credential sent with `connect`, and a device a bridge follows to a new address, are protected
  by the protocol's own authentication in the bridge.

HS27's fake `_hue._tcp` is the case of a new candidate. A hijacked existing key is the case the
readers should look for.

### Scenarios

HS27 (new): a satellite and a plug, found. HS10 (the new lamp), HS17 and HS18 touch provisioning
and should be re-walked.

## Pass 1

Green on `84d0e0b`: the manifest check, the conformance unit tests (the manifest schema's
included, which validate the example manifest printed in the bridge standard), the
private-reference grep and the numbering grep.

**Departures from the plan made while writing.**
- `candidates` takes `{ ignored? }`, so the owner can find an ignored candidate to unignore; the
  spec's operation had no way to list one.
- The `connected` and `connect_failed` bridge events carry the `requestId`, so the applier can tie
  the event to the `connect` it sent.
- Negative subjects were added for every new id, beyond the spec's list: `bad-manifest`,
  `partial-connections`, `finder-dies-silently`, `candidates-late`, `hides-an-off-source`. The
  spec's `connect-adopts` became `connect-ignored` in spec review.
